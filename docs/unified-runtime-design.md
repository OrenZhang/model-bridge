# 统一模型、工具执行与分发方案

2026-11-07。本文记录已验证的实现和后续设计。

## 产品边界

客户端只选择模型并使用 Responses、Messages 或 Chat Completions。网关根据所选模型的可用连接、原生接口和工具能力执行请求，返回客户端原来的协议。模型名称不添加账号前缀，同名模型跨账号和通道合并。

协议统一不意味着模型天然具备所有能力。函数调用、工具发现、搜索、网页读取、图片输入、结构化输出、服务端会话和异步任务分别建立能力记录：原生执行、适配执行、需要配置执行端、不可用。不可用时返回可处理的错误，不能删除工具后声称完成。

工具有两种执行位置：

- 客户端工具：Codex 的文件、终端、MCP 和动态工具发现，仍由客户端执行，网关保持定义、namespace、call ID、结果和历史。局域网客户端调用不会变成在网关电脑上执行命令。
- 网关工具：联网搜索、网页读取及用户接入的远程工具，在 Model Bridge 中集中执行。结果带来源与状态，进入模型的下一次推理。密钥仅留在网关。

模型池只在新对话时选择账号。已有对话、thinking、工具发现与工具结果固定原账号；收到历史却无法确认归属时明确拒绝。

## 采用的开源技术与参考实现

| 部分 | 选择 | 用途与取舍 |
| --- | --- | --- |
| 模型请求与流 | 保留 TypeScript / Node、Undici、现有 SSE 编解码 | 已有代理隔离与连接复用。先消除阻塞、重复处理和缓存整段输出；当前基准不支持为转换性能重写整个内核。 |
| 工具连接 | 官方 MCP TypeScript SDK | 接入本机 stdio 或远程 Streamable HTTP 工具，维护定义、连接生命周期、取消和能力变化。固定依赖版本并按该版本协议实现，不假设不同版本通知格式相同。 |
| 工具参数校验 | 拟采用 Ajv，按 schema 版本编译缓存 | 工具注册时编译，调用时复用验证器；不在每次请求里重新编译全部 JSON Schema。 |
| 搜索执行端 | SearXNG 适配器，另提供 Tavily API 适配器 | 前者支持用户自己的开源搜索服务；后者使用正式搜索 API。桌面端只集成适配器，不把搜索引擎整套打进安装包，不依赖随机公共实例。 |
| 会话持久化 | 拟采用 SQLite WAL，单独存储工作线程 | 以事务只更新绑定和游标相关行，避免每个新对话重写全部 JSON。提交成功后才调用上游；旧 JSON 一次迁移且保留备份。需要先验证 Node 与打包 Electron 在五个目标平台上的支持。 |
| 服务商兼容 | 参考 LiteLLM 的适配范围及测试思路 | 本项目继续独立实现；不再嵌套一层完整模型网关，避免出现两套路由与协议转换。 |
| 订阅认证 | 参考 CLIProxyAPI 的 OAuth、多账号和协议兼容设计 | 保留本项目已工作的官方登录助手与账号隔离，不为复用而引入第二套凭据管理。 |
| 路由算法 | 借鉴 Envoy P2C 与 Linkerd EWMA | 实现轻量调度器，不在桌面应用里部署服务网格。算法收益需要用本项目的长流式请求和账号限额验证。 |

## 请求与工具执行过程

1. 验证访问 Key、模型可见性、工具访问范围及请求大小。
2. 查询按配置版本编译的模型路由表；不在每次请求中重建所有模型分组。
3. 恢复会话绑定；新对话先筛选支持所需图片、thinking、工具和协议的连接，再做负载选择。
4. 优先该连接的原生接口。需要转换时，使用统一且有序的消息/工具/推理事件结构。
5. 普通函数与客户端工具发现返回客户端执行。网关工具进入有次数、并发、超时和取消限制的执行循环。
6. 把真实工具结果送回原模型和原账号，再继续流式响应；记录每次模型调用和工具执行的状态与开销。

OpenAI `tool_search` 的 `execution: client` 不能删除，也不能作为普通函数名直接返回：上游可以收到适配后的函数定义，下游必须恢复 `tool_search_call`，客户端回传的 `tool_search_output.tools` 则载入下一次请求。namespace 和调用结果要贯穿后续轮次。

网关搜索先实现搜索，再补网页读取与页内查找，分别验证行为；不能把只会返回摘要的搜索端宣称为完整浏览器。搜索结果统一为来源 ID、URL、标题、摘要、时间与获取状态。模型最终引用必须关联实际返回来源；不生成虚构 URL 或引用。Responses、Messages 和 Chat 的工具声明与输出格式分别适配，不把一种协议的托管工具原样塞给另一种协议。

工具注册项包括 schema、执行端、凭据引用、网络配置、超时、最大并发、结果大小和是否有副作用。客户端工具的权限与确认由客户端保留；首批网关内置工具限于搜索和网页读取。

## 调度算法

已有会话先查绑定，通常一次内存索引即可完成。以下算法只影响新对话：

1. 能力筛选：精确匹配模型名和请求能力；隐藏、停用、认证失败、冷却中的连接不参与。
2. 对称账号继续支持轮询。异构连接提供自适应模式，使用 P2C：抽取两个候选，比较延迟和在途负载。
3. 可试验的评分为 `TTFT_EWMA × (inflight + 1) / weight`。这是本项目待验证的启发式，不是 Envoy 或 Linkerd 原始公式。权重表示账号期望份额，值越低越优；加入冷启动样本和少量探测，避免永远不再选择曾经慢过的账号。
4. 对流式模型，延迟样本主要取首个有效 token，而不是响应头或完整生成时间。在途数保留到流结束；长请求不会仅因完成时间长就被当成坏节点。
5. 429 遵循 `Retry-After`；认证失败等待凭据更新；网络/5xx 连续失败进入熔断，少量半开探测恢复。新对话绕开坏通道，已发送请求与有账号状态的续聊不换号重试。
6. 每账号并发上限加有界队列。满载快速返回明确错误和重试信息，避免无限排队。

不能通过算法强迫不同模型具备同样质量或速度。用户指定的模型不做语义改写；不额外调用另一个 LLM 来决定普通请求发给谁。

## 工具发现与缓存

网关自有工具目录使用名称精确匹配、能力标签过滤、BM25 排序及 Top-K schema 预算。Codex 自己的工具发现仍交由 Codex 执行，网关只适配协议，避免维护重复索引。

- 常用基础工具保持直接可见，动态目录只按需加载，减少每轮工具定义和模型预填充开销。
- 模型目录按配置版本缓存；工具目录按服务连接与定义版本缓存，变更时失效。
- 搜索缓存键含执行端、访问范围、查询和过滤参数；只合并同一范围的相同在途查询。短 TTL 可缓存公开搜索结果，失败不当作空结果缓存。
- 默认不跨用户缓存模型回答、私有工具结果、账号鉴权或 thinking。

## 本机基准

执行命令：`npm run build && node scripts/benchmark-routing.mjs`。2026-11-07，Apple M2 / macOS arm64 / Node 22.22.2。使用纯合成账号、请求及临时文件，不读取本机凭据。

| 场景 | 样本 / 并发 | P95 |
| --- | --- | --- |
| 约 24 KB Responses 请求转换为 Chat | 500 / 单次测量 | 0.085 ms |
| 约 24 KB Responses 请求转换为 Messages | 500 / 单次测量 | 0.079 ms |
| 新会话路由，JSON 落盘，初始 0 个归属 | 128 / 1 | 0.410 ms |
| 新会话路由，JSON 落盘，初始 1,000 个归属 | 128 / 16 | 17.807 ms |
| 新会话路由，JSON 落盘，初始 5,000 个归属 | 128 / 16 | 83.101 ms |

这些数据分别测请求转换，以及含排队和原子文件替换的账号选择。没有包含 HTTP、SSE 输出、局域网、模型或搜索耗时，不能相加成端到端 SLA，也不能据此宣称高并发服务能力。原始数据见 [routing-m2-2026-11-07.json](benchmarks/routing-m2-2026-11-07.json)。

当前可确认的问题是会话表增长会放大新对话写盘与排队；不是 JSON 字段转换本身耗费数秒。还需要单独测量跨协议输出：现有 Chat → Messages 分支为了保持 thinking 签名和块顺序，存在等到生成结束再 flush 的情况。不能用较快的响应头掩盖首个有效文本迟迟不到。

新增计时应覆盖认证/路由/持久化排队、上游建连与首 token、工具排队与执行、转换与写出、总耗时及 token/s。按 Key、连接、模型、入口协议和工具类型聚合，维持最近 60 天；常规统计不保存消息、密钥与推理正文。
